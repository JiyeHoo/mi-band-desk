# 蓝牙底座功能扩展调研

日期：2026-09-23。对象：已连接本机的“小米手环多功能桌搭1635”。范围：macOS 侧能力调研；未开发业务功能、修改底座固件或部署手环。

## 结论

**可以开发，最有价值的是把底座用作机器人的耳朵、扬声器和部分实体控制入口，由 Mac 承担计算与业务逻辑，手环显示表情和状态。** 不需要先取得底座的固件开发能力。

语音播报、语音输入和媒体控制有现成系统接口；机器人表情联动需要扩展现有 Mac／AstroBox／手环应用。**长按麦克风键直接替换 Siri 为自定义助手，仍需单独验证，不能作为首版已确定的前提。** 保留 Siri，通过快捷指令启动自己的功能，是有官方支持的替代入口。

本轮只验证设备枚举、缓存服务、HID 描述符与现行项目代码；没有录音、播放测试音、捕获按键事件、切换默认音频设备或改绑 Siri。

## 本机证据

本机系统：macOS 26.4.1 / 25E253。以下信息来自本轮实时读取，不沿用旧版本记忆。

| 检查 | 结果 | 证据边界 |
| --- | --- | --- |
| 蓝牙连接 | 目标已连接；系统分类 Speaker；报告固件 2.4.0 | 这是底座信息，不是手环 OS 3.1.32 |
| 系统服务 | `HFP AVRCP A2DP HID ACL` | ACL 是链路类型，不是额外业务能力 |
| 音频输入 | 底座为默认输入；1 通道，16,000 Hz，Bluetooth | 枚举可用输入，不代表已经验证拾音距离、识别率或实际编码 |
| 音频输出 | 底座为默认输出及系统声音输出；2 通道，44,100 Hz | 是当时的枚举状态，不保证开麦时维持该规格 |
| 缓存 SDP | `JL_HFP`、`JL_A2DP`、`JL_HID`；匹配 0x111E、0x110B、0x1124，以及 AVRCP 0x110C／0x110E／0x110F | 仅读取系统缓存，没有发起服务发现或重新连接；服务名不足以确定芯片型号 |
| HID | Consumer Control，Usage Page 0x0C / Usage 0x01，Report ID 3 | 存在媒体控制入口，尚未证明某个物理按键实际发送哪个事件 |
| 麦克风键长按 | 用户报告会唤醒 macOS Siri | 本轮没有重新按键复现或抓取 HFP 指令 |

HID 描述符声明了 13 个一位输入，其中包括：

| Usage | 含义 |
| --- | --- |
| 0xCD | 播放／暂停 |
| 0xB5 / 0xB6 | 下一首／上一首 |
| 0xE2 | 静音 |
| 0xE9 / 0xEA | 音量增加／减少 |

其余声明为 Home、Search、Screen Saver、Eject、Snapshot、Forward、Stop。它们是描述符能力列表，**不等于底座具有全部对应实体按钮**；也不等于全都允许可靠地改绑。当前描述符未包含标准 Voice Command（0xCF）。对应名称已与本机 SDK 的 `IOHIDUsageTables.h` 核对。

缓存中另见 0xAE00、0xBF00 等未分类服务，本轮未解析其协议。未发现标准 SPP 0x1101 匹配；不能因此断言厂商没有私有接口，也不能把这些条目当作已知的 DIY 数据通道。底座 BLE 协议不在本轮扩展范围。

复查入口：`system_profiler SPBluetoothDataType SPAudioDataType -json`、`ioreg -r -c IOHIDDevice -a`，仅提取目标设备白名单字段；SDP 使用 `IOBluetoothDevice.pairedDevices` 和 `services` 缓存。不要直接保存／分享完整系统转储，其中可能包含其他设备与地址。只读 SDP 探针在本机 `.artifacts/base-bt-research/`，该目录不会自动随项目交接；以上 API 和表格是可重建依据。

## 可以做的功能

表中“可行”表示设备能力与系统 API 支持该方向，不表示产品功能已实现或真机验收。

| 方向 | 具体体验 | 判断与依赖 |
| --- | --- | --- |
| 机器人语音播报 | 报时、番茄钟结束、额度不足、任务完成后说一句话 | **优先做**。Mac 合成／播放音频，底座输出；各业务事件需独立接入，现有额度桥没有任务完成事件 |
| 语音快捷操作 | 长按 → Siri → 说“桌搭专注”“桌搭播报额度” → 执行动作 | **优先验证**。Siri 调用快捷指令有官方支持；快捷指令及桥接动作尚需创建和联调 |
| 自定义语音助手 | 听问题、语音转文字、调用模型／本地工具、从底座回答 | **技术路线可行**。需要新 Mac 语音模块、麦克风授权、识别／对话／合成引擎；物理麦克风键入口另算 |
| 机器人表情联动 | 听时专注、等待时思考、回答时开心、失败时困惑 | **可扩展**。由 Mac 发语义状态，手环播放本地动作；当前协议不支持这些状态 |
| 实体遥控 | 播放／暂停播报、打断回答、切换功能或表情 | **条件可行**。先测短按／长按实际事件和系统分发；不能凭 HID 描述符直接承诺 |
| 语音便签／口述输入 | 按入口后说一句话，Mac 转成文字或草稿 | **技术路线可行**。仍需录音／识别质量和目标应用入口验证 |
| 音乐／专注桌搭 | 音乐、白噪声、计时、简单播放状态表情 | **可行**。普通播放最简单；跨播放器的曲名、进度和控制权限需逐应用核对 |
| 自定义唤醒词 | 说“机器人”后直接交互 | **放后面**。可在 Mac 常驻处理音频；没有证据证明底座提供可编程的离线唤醒词能力 |

Apple 提供 [Speech](https://developer.apple.com/documentation/speech) 语音识别和 [AVSpeechSynthesizer](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer) 合成接口。具体中文语言资源、离线条件和当前系统适配仍应在实现时验证；也可选独立识别／对话服务。现有 Codex 额度采集链路不等于通用语音或模型调用接口。

## 长按麦克风键为什么唤醒 Siri

结合设备提供 HFP、用户观察到 Siri 唤醒，以及当前 HID 描述符没有 Voice Command，**优先假设**它发送了 HFP 的语音识别激活命令，例如 `AT+BVRA=1`。这是待抓取的解释，不是本轮已观察到的协议报文。HFP 的此类机制可见 [Bluetooth HFP 规范入口](https://www.bluetooth.com/specifications/specs/hands-free-profile/) 与 [Google 的 BVRA 时序说明](https://developers.google.com/assistant/accessories/integrate/bluetooth/voice-optimization)。

三条路线要分开评估：

1. **保留 Siri 入口。** 长按后说自定义快捷指令名称，由快捷指令执行脚本、调用应用动作或新建的本机业务接口。Apple 明确支持 [在 Mac 上通过 Siri 运行快捷指令](https://support.apple.com/zh-cn/guide/shortcuts-mac/apd07c25bb38/mac)。这依然经过 Siri，通常要说出指令名称，不能描述成按一下直接进入自定义助手。
2. **接收媒体／HID 事件。** 对播放暂停等键做映射实验。Apple 的 [MPRemoteCommandCenter](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter) 能处理外部附件和系统媒体控制，但它属于媒体命令分发，不是任意蓝牙按键的全局独占入口。音乐 App 的竞争、前后台、输入监控权限和事件抑制都需实测。音量键不宜默认挪用。
3. **研究 HFP 接管。** Apple 存在公开的 [IOBluetoothHandsFreeAudioGateway](https://developer.apple.com/documentation/iobluetooth/iobluetoothhandsfreeaudiogateway)，可以处理 AT 命令。本机 SDK 也有 `processATCommand:`。但这不是“监听系统已持有连接并替换 Siri”的现成接口；与系统 HFP 服务共存、连接归属、SCO 音频、重连后的路由尚未验证。列为探索项，不能因为 API 存在就承诺能接管。

仅关闭 Siri 或修改 Siri 的键盘快捷键，不能据此推断底座长按就会变成可供任意应用读取的按键。本轮没有修改这些设置。

## 适合本项目的架构

```text
底座麦克风 ── HFP 输入 ──> Mac 语音／业务模块
底座扬声器 <── BT 音频 ─── Mac 语音／业务模块
                              │
                        语义状态／操作事件
                              ↓
                  扩展后的 AstroBox 插件
                              ↓
                    手环表情／状态／操作
```

底座音频链路与手环应用通信是两条独立链路，Mac 负责协调。没有证据证明手环应用可以直接接管底座 HFP、直接驱动扬声器或独立运行这一套语音助手；Mac 离线／休眠时，这套自定义功能也不能假定仍工作。

可复用现有 Mac 原生菜单栏 App 和 AstroBox 连接方式，但要新增明确的业务模块及消息协议：

- 当前 [Mac 实现](../macos/BandDeskBridge/Native/main.m) 每 120 秒采集额度；[插件](../astrobox-plugin/band-desk-bridge/src/lib.rs) 每 15 秒取快照；它们不适合作为实时语音状态更新节拍。
- 当前 [手环解析器](../src/common/codex-card.js) 和插件均限制 `schemaVersion=1`、`cardId=codex.rate-limits`。新增 `listening / thinking / speaking / idle / error` 应设计独立消息类型与白名单，不能把语音状态伪装成额度快照或放宽现有校验。
- 手环只接收状态和动作，音频处理留在 Mac。先做一句话或阶段级联动，不承诺节拍／音素级同步；新链路时延必须真测。
- 新事件应有会话、序号、有效期、幂等与确认；用户手动输入优先，断连或过期自动回到普通桌面，继续保留生命周期与原生分页约束。

这里的状态名与架构是调研建议，尚未批准为正式协议或写入运行代码。

## 音质与交互限制

**底座开麦可能让播放音质下降。** Apple 明确说明，传统蓝牙设备从高质量播放转为双向语音模式时，音质会降低，直到不再使用其麦克风。当前枚举出的“输入 16 kHz、输出 44.1 kHz”不能证明同时开麦仍有双声道高质量输出。见 [Apple 音质说明](https://support.apple.com/zh-cn/102217)。

首版适合“触发 → 听一句 → 停止采集 → 回答”，并检查系统何时释放通话音频模式。要边放音乐边随时说话，可考虑 Mac 内建麦克风负责拾音、底座只输出，但体验取决于摆放与拾音距离。持续双向对话还需验证回声抑制和打断，不能把扬声器回放再次识别成用户指令。

音频路由应绑定选定设备并监听断连，不依赖永远保持系统默认；断连时应暂停或按明确设置回退，避免播报意外从其他输出设备响起。录音只在清楚的交互状态中启动，结束后及时释放。

## 建议开发顺序与验收

### 新增交互目标：按住语音输入，松手发送到 ChatGPT

用户进一步明确：希望按底座按钮时直接进入 ChatGPT 语音输入，持续按住期间录音，松开后发送。该目标优先于上一轮泛化的语音机器人建议；当前仍在可行性确认，未实现。

**交互可设计，原麦克风键是否适用取决于它是否提供真实的按下／松开事件。** 一次 Siri 唤醒信号不包含“仍按住”的持续状态；HFP 语音识别开始／结束也不能直接当成物理按下／松开。即使观察到媒体键 1／0，也需确认间隔随实际持按变化，排除固件生成的固定长度脉冲。

2026-09-23 官方资料核对：

- [ChatGPT 语音听写](https://learn.chatgpt.com/docs/prompting#use-voice-dictation)：输入区可见时可按 `Ctrl+Shift+D` 启动，识别结果进入输入框供检查和编辑，之后再发送。文档没有说明普通听写快捷键在松开时自动发送。
- [Codex Micro](https://learn.chatgpt.com/docs/features/codex-micro)：该专用附件的 Mic 键支持按住录音、松开停止，转写准备好后仍需按 Codex 键发送。这说明客户端存在这种交互，但不能据此推断普通蓝牙音响自动兼容其附件集成。
- [ChatGPT Voice](https://learn.chatgpt.com/docs/features/voice) 是实时语音对话；本需求优先按“语音听写进入当前对话并发送”理解，不把启动 Voice Chat 当成已经满足。
- [Realtime API 的 Push-to-talk](https://developers.openai.com/api/docs/guides/realtime-conversations#push-to-talk) 明确支持应用控制录音开始、松开后提交并触发回答。这是另做 API 客户端的路线，不等于发送到现有 ChatGPT 对话或沿用其订阅权益。

建议分两道验证：

1. **底座事件。** 对原麦克风键分别持按约 1／3／5 秒，观察是否有可靠的开始和结束、结束是否紧随真实松手；同时检查 Siri 冲突。没有松开信号时，不能实现这颗键的精确“松手发送”，只能再研究其他键、按一次开始／再按一次结束，或独立控制器。
2. **ChatGPT 客户端。** 先证明可靠的开始听写、结束听写、转写完成和发送入口。Mac 桥应在松开后停止采集，等转写完成再仅发送一次；不能在松开瞬间盲发 Enter，也不能用固定延迟猜测转写已完成。目标对话变更、取消、空转写、断连或超时必须取消本次自动提交。

本机只读确认 `/Applications/ChatGPT.app` 版本为 26.917.51856 / 10492，bundle ID 为 `com.openai.codex`。Computer Use 工具因安全限制拒绝访问该应用窗口，因此没有查看其实际设置、触发听写、录音或发送消息，也未通过其他 UI 技术绕过。以上客户端能力依据官方文档，不是本机联调通过。

首次按键补测：用户两次长按，确认 Siri 在持按期间出现。目标专用 IOHIDManager 探针匹配 1 台设备且非独占打开成功，但未收到对应 Consumer 输入值；独立输入监听权限检查为 granted。仍缺少音量键等正对照，也没有 HFP 报文证据，因此暂不能判定是否存在物理松手信号。详见 [验证记录](validation.md)。

### 后续完整语音机器人路线

1. **音频最小闭环。** Mac 手动入口录一句、识别、从底座播报；验证实际收音、中文识别、输出设备、模式切换与停止。同步做一条 Siri 快捷指令入口。此阶段不依赖麦克风键接管。
2. **实体键验证。** 只监听目标底座的事件，逐个记录短按／双击／长按／松开，与 Siri 出现时间对应；验证前后台、播放器正在运行、睡眠后重连。先得出按键矩阵，再决定接管哪个键；HFP 路线若需改变系统连接行为，独立设计实验。
3. **机器人联动。** 新协议传递听／想／说状态，手环使用本地动作。测状态到达、取消、断连恢复、输入优先和音画延迟；不能直接复用 15 秒额度轮询。
4. **按需增加业务。** 播报额度、专注计时、语音便签；任务结束播报、日历等需接入对应可信事件来源。

推荐第一项产品目标为：**“能听一句、答一句、有表情反馈的桌面机器人”**。第一轮先证明音频和触发可靠，之后再把“长按原麦克风键直接唤醒自己的助手”作为单独能力判定。

当前交付状态：**调研及文档已完成；新功能未实现、未构建、未安装、未获真机验收。** 手环 0.9.2 / v21、Mac 0.8.2、插件 0.7.6 的既有状态保持，详见 [交接](handoff.md)。
